# Project Specification — Sight Reading Trainer

## Current V1 Implementation Decisions (Updated 2026-08-30)

These decisions override older or broader statements elsewhere in this document where they conflict.

* Primary supported platform: current Google Chrome desktop on macOS and Windows.
* Primary hardware path: USB MIDI through the Web MIDI API.
* Edge Chromium and Bluetooth MIDI are best-effort. Safari and mobile Web MIDI are not V1 release blockers, but every page must remain readable and operable at a 360 px mobile viewport without document-level horizontal overflow.
* Responsive mobile layout includes compact navigation, stacked cards and controls, reflowed sheet-music measures, a horizontally scrollable touch piano, responsive dashboard charts, and a wrapped pitch heatmap. Chrome Desktop + USB MIDI remains the formally supported training path.
* Mobile landscape at 800 × 360 is an explicit layout acceptance target: training uses a full-width vertical stack with notation on top and the virtual piano below. Sheet Reading uses a single four-measure row whenever space permits.
* MIDI permission, status, and device selection live in a persistent top-navigation menu rather than inside the training canvas. The MIDI connection survives client-side navigation between training modes.
* Focus Mode is available in both Reflex and Sheet Reading. It hides the application header outright, MIDI menu included, and the training toolbar with it, so only the notation and the virtual piano remain. This reverses the earlier decision to keep a compact header for MIDI access: the connection is owned by the layout-level provider and survives, and leaving focus brings the menu, the session counters, and pause back.
* The only control inside Focus Mode is a small Exit Focus button overlaying the top-right of the notation, positioned so it costs no layout space. Correct and incorrect verdicts stay legible through note colour, and the verdict text is kept for screen readers only.
* Reflex notation scales up to fill the height Focus Mode frees, to a ceiling beyond which it reads as stretched against the unchanged horizontal spacing. Leftover height goes to the virtual piano. Sheet Reading keeps its natural notation size for now.
* Reflex presents a continuous note stream rather than one note swapped in place. Reading runs left to right, so notes travel right to left: upcoming notes enter at the right edge, the armed note sits under a fixed playhead about a quarter of the way across the staff, and answered notes fade out past the clef. Four to six notes stay visible ahead depending on staff width. The clef and staff lines never move.
* The stream is still self-paced: it advances only on a correct input, never on a clock. Tempo-driven continuous reading remains Performance mode and stays out of V1.
* Bluetooth devices are supported when the operating system exposes them to Chrome as a Web MIDI input. V1 will not implement a separate Web Bluetooth/BLE-MIDI protocol stack.
* V1 remains a complete product slice: Reflex, Sheet Reading, virtual piano, computer keyboard, MIDI, audio, adaptive practice, private Supabase Auth/history, dashboard, settings, and an installable desktop PWA.
* V1 is a private application. `/train`, `/dashboard`, and `/settings` require a valid non-anonymous Supabase session. Access is granted or revoked by creating or deleting users in the Supabase dashboard; no separate application allowlist is required.
* Public sign-up and guest training are disabled. The application does not expose a `/signup` route. Approved accounts are created manually by the owner in Supabase, and public user registration must be disabled in Supabase Authentication settings.
* The application fails closed if Supabase public configuration is absent or the request has no valid authenticated session. The landing page, login page, and authentication callback remain public.
* IndexedDB is used only as a pending cloud-save queue if authentication or Supabase connectivity is interrupted after a private training session has already started. It is not a guest-history store.
* Vercel is the primary runtime and deployment target. Local execution is for development verification only; production configuration, routing, security headers, and environment variables must work on Vercel.
* PWA V1 is installable in standalone landscape mode but does not promise offline training or a service worker cache. The manifest uses stable ID `/train` for compatibility with earlier installs, public launch URL `/`, full scope `/`, and both general and maskable 192/512 launch icons.
* UI language is English for V1.
* Treble clef and natural notes are the only scored notation in V1. The domain model must still preserve written pitch spelling separately from sounding MIDI pitch.
* Performance mode, native mobile applications, bass/grand staff, advanced rhythm, MusicXML, and full offline sync remain future work.

### V1 Metric Definitions

* Accuracy means first-attempt accuracy: targets answered correctly on the first input divided by targets completed.
* Mistakes means the total number of incorrect note-on inputs.
* Correct response time runs from the moment the rendered target is armed to the first correct input. Incorrect inputs do not restart that timer.
* A training trial represents one displayed target; a trial may contain multiple input attempts.
* In the Reflex stream a note is readable before it is armed, so response time measures the reflex from playhead arrival, not from first sight. This is the intended read-ahead training effect, but it makes Reflex response times recorded before the stream landed non-comparable with later ones. Sheet Reading already had the same read-ahead property.

### Delivery Order

Build V1 as deployable vertical milestones: foundation and core logic, playable Reflex, MIDI/audio, Sheet Reading, Supabase persistence, adaptive training/dashboard, then production hardening. Each milestone must remain deployable to Vercel.

## 1. Project Overview

Build a web application for practicing piano sight-reading and music-note recognition.

The main goal is not simply to teach note names. The application should train the complete loop:

Visual notation → recognition → physical response → accuracy → speed

The application should initially focus on treble-clef note reading, especially ledger-line notes above and below the five-line staff.

The architecture must be designed from the beginning so the project can later support:

* Bass clef
* Grand staff
* Both hands
* Rhythm
* Chords
* Intervals
* Scales
* Arpeggios
* MIDI keyboard input
* Velocity
* Sustain pedal
* Adaptive training
* Full sight-reading exercises
* User progress/history
* Difficulty progression

The application will be deployed on Vercel and use Supabase for authentication and persistent data.

---

# 2. Primary Goal

The application should help the user progress from:

"I need to calculate which note this is"

to:

"I recognize the note immediately"

and ultimately:

"I recognize groups, intervals, and musical patterns while reading ahead."

The application should therefore measure more than accuracy.

It should record:

* Note recognition speed
* Accuracy
* Performance per MIDI pitch
* Performance by note range
* Ledger-line performance
* Mistake patterns
* Session performance
* Historical improvement

# 4. Important Architecture Principle

The application must separate:

1. Music/game logic
2. Input
3. Audio
4. Rendering
5. Persistence
6. UI

The game engine MUST NOT care whether the player entered a note using:

* Mouse/touch piano
* Computer keyboard
* MIDI keyboard

Every input system should normalize its input into the same structure.

Example:

```ts
type NoteInputEvent = {
  midi: number
  velocity: number | null
  source: "touch" | "computer-keyboard" | "midi"
  timestamp: number
}
```

Example:

Middle C:

```ts
{
  midi: 60,
  velocity: 84,
  source: "midi",
  timestamp: performance.now()
}
```

All game modes consume this normalized event.

This is an important requirement.

Do not embed MIDI-specific logic directly inside the training components.

# 5. Music Data Model

Internally, notes should primarily be represented by MIDI note number.

Example:

```ts
type MusicNote = {
  midi: number
  letter: "C" | "D" | "E" | "F" | "G" | "A" | "B"
  accidental: "natural" | "sharp" | "flat"
  octave: number
}
```

Examples:

```txt
C4 = MIDI 60
D4 = MIDI 62
E4 = MIDI 64
C5 = MIDI 72
```

Create centralized helper utilities for:

```ts
midiToNote()
noteToMidi()
midiToVexFlowKey()
getLedgerLineCount()
getStaffPosition()
getClefRange()
```

Do not duplicate conversion logic throughout the application.

# 6. V1 Scope

V1 should contain three main training modes.

## Mode A — Reflex Trainer

Purpose:

Train instant recognition of individual notes.

Flow:

1. Display a stream of notes on the staff, with the armed one under the playhead and the next several already readable to its right.
2. Start timer when the armed note reaches the playhead.
3. User enters a note.
4. Determine correct/incorrect.
5. Record response time.
6. Give quick visual feedback.
7. Slide the stream one note to the left so the next note reaches the playhead.
8. Continue until session target is reached.

Default:

```txt
Notes per session: 50
```

Settings:

* 25 notes
* 50 notes
* 71 notes
* 100 notes
* Endless

User should be able to select note range.

Examples:

```txt
Staff only
Staff + 1 ledger
Staff + 2 ledgers
Staff + 3 ledgers
Custom MIDI range
```

Initial clef:

```txt
Treble
```

Architecture must support bass clef later.

---

# 7. Reflex Trainer Timing

Timing accuracy matters.

Use:

```ts
performance.now()
```

Do not use `Date.now()` for reaction timing.

When the note is rendered and ready:

```ts
noteShownAt = performance.now()
```

When valid player input is received:

```ts
responseAt = performance.now()

responseTimeMs = responseAt - noteShownAt
```

Important:

Incorrect notes should NOT reset the original timer.

Example:

Target = A4

User:

```txt
G4 at 600 ms ❌
A4 at 1100 ms ✅
```

Record:

```txt
firstAttemptMs = 600
correctResponseMs = 1100
attemptCount = 2
```

This lets us distinguish:

* Fast and correct
* Fast but inaccurate
* Slow but accurate

---

# 8. Reflex Trainer Feedback

Correct:

* Brief green feedback
* Play note
* Advance quickly

Incorrect:

* Brief red feedback
* Keep target visible
* Do not immediately reveal answer unless configured
* Allow another attempt

Do NOT use long animations.

Training speed is important.

Target transition delay should be roughly configurable around:

```txt
100–300 ms
```

Add:

```txt
Instant next note
Small delay
```

as user settings.

---

Purpose:

Train behavior closer to real sheet music reading.

Unlike Reflex mode, multiple notes should be visible simultaneously.

Example:


Initial implementation may simplify rhythm to quarter notes.

V1 Sheet Reading:

* Treble clef
* 4/4
* Quarter notes
* Single notes
* No accidentals initially
* No chords
* No rests initially

Suggested default:

```txt

16 notes
```

Difficulty options:

```txt

Medium
Hard

```

# 10. Sheet Reading Cursor

The current expected note should be visually highlighted.

Example:

```txt

note 2
note 3 ← current
note 4
```

Highlight should NOT obscure notation.

After a correct input:

```txt

```

```txt

```

Wrong note does NOT advance.

# 11. Mode C — Performance / Continuous Reading

Create architecture for this mode but it does not need to be fully featured in the first implementation.

Goal:

Replicate real sight-reading.

Rules:

* Music continues at a fixed tempo.
* User should not stop.
* Wrong notes are recorded but do not pause the exercise.
* Cursor continues according to musical time.

Future settings:

```txt
40 BPM
50 BPM
60 BPM
80 BPM
100 BPM
120 BPM
```

Metronome support should be possible.

Do NOT make this a blocking requirement for initial MVP.

# 12. Note Generation Engine

Do NOT simply use:

```ts
Math.random()
```

inside React components.

Create a separate note generation module.

Suggested interface:

```ts
interface NoteGeneratorConfig {
  clef: "treble" | "bass"
  minMidi: number
  maxMidi: number
  naturalsOnly: boolean
  adaptiveMode: boolean
  avoidImmediateRepeat: boolean
}
```

Function:

```ts
generateNote(config): MusicNote
```

For sequences:

```ts
generateSequence(config, length): MusicNote[]
```

---

# 13. Randomization Rules

Avoid poor random sequences.

For example:

```txt
C C C C C
```

should rarely occur unless intentional.

Default:

```txt
avoidImmediateRepeat = true
```

V1 random generation should be uniformly distributed within the selected note set.

Later adaptive mode will override uniform probability.

---

# 14. Adaptive Training System

This is one of the most important future features.

The system should learn which notes the user struggles with.

For every note, calculate:

```txt
attempt count
correct count
incorrect count
accuracy
average reaction time
median reaction time
best reaction time
recent reaction time
```

Example:

```txt
F5
Accuracy: 98%
Average: 340 ms

A5
Accuracy: 83%
Average: 1,280 ms
```

The system should eventually increase the probability of A5.

Suggested future formula:

```txt
difficultyWeight =
  reactionTimeWeight
  × errorWeight
  × recencyWeight
```

Do NOT implement an overly complicated ML system.

Simple weighted random selection is enough.

---

# 15. Adaptive Selection V1

Once basic statistics exist, implement:

```txt
70% weak/problem notes
30% normal random notes
```

But avoid repeatedly showing one note.

Suggested constraint:

Do not show the same note more than twice within the last 5 generated notes unless the note pool is very small.

* easier CSS interaction
* individual SVG elements
* cleaner resizing
* easier future highlighting

```txt

```


# 49. Row Level Security

Every user-owned table must have RLS enabled.

User should only:

```txt
SELECT their own rows
INSERT their own rows
UPDATE their own rows
DELETE their own rows where appropriate
```

Use:

```sql
auth.uid() = user_id
```

Do not use service-role keys in browser code.

Never expose:

```txt
SUPABASE_SERVICE_ROLE_KEY
```

to the client.

# 50. Client vs Server Responsibilities

Client:

* Training loop
* VexFlow rendering
* MIDI input
* Touch input
* Computer keyboard input
* Audio
* Low-latency timing
* In-session state

Server/Supabase:

* Authentication
* Persistence
* Historical stats
* Session summaries
* Dashboard queries

Do NOT send a network request after every MIDI event if avoidable.

Training must remain responsive even with slow internet.

---

# 51. Session Persistence Strategy

During training:

Keep attempts locally in memory.

Example:

```ts
const attempts: Attempt[] = []
```

At session completion:

Batch insert attempts into Supabase.

Also persist session summary.

This prevents network latency from interfering with training.

Optionally periodically checkpoint longer sessions later.

---

# 52. Offline / Connection Failure

If Supabase save fails:

Do not lose the completed session.

Store unsynced session locally.

Example:

```txt
localStorage / IndexedDB
```

Mark:

```txt
syncStatus = pending
```

Retry later.

This can be Phase 2 if necessary.

# 55. Performance Requirements

Reaction timing should not depend on:

* Supabase
* React rerender latency
* network calls

Use high-resolution browser timing.

Keep MIDI event path short:

```txt

→ session engine
→ correctness
→ feedback
```

# 67. Weak Note Detection

A note should be considered weak if one or both are significantly worse than the user's average:

```txt
reaction time
accuracy
```

Do not define weakness purely by mistakes.

Example:

```txt
A5
100% accuracy
1.6 sec average
```

This is still a weak note compared with:

```txt
E5
100%
0.35 sec
```

---

# 68. Median Response Time

Always calculate median in addition to average.

Reason:

One distraction may create:

```txt
8,000 ms
```

and distort average.

Dashboard should emphasize:

```txt
Average
Median
```

# 69. Outliers

Do NOT silently delete slow responses.

For analytics displays, optional trimmed averages may be introduced later.

Raw data remains authoritative.

#### PWA standalone installation

The production manifest must provide a stable app identity, public same-origin launch URL, full application scope, and `any` plus `maskable` PNG icons. An installed app must launch from its operating-system icon as well as Chrome's “Open in app” action.
